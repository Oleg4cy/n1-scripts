# Скрипты настройки N1 API

Этот документ описывает комплект скриптов из архива `n1-api-setup-scripts.zip`.

Комплект предназначен для развёртывания Laravel API N1 на Debian 13 с Nginx, PHP 8.4, PostgreSQL и GitHub-доступом по SSH.

## Рекомендуемый порядок запуска

1. `00-audit-api-host.sh`
2. `01-install-api-runtime.sh`
3. `02-create-n1-user-and-ssh.sh`
4. Добавить выведенный публичный SSH-ключ в GitHub и проверить доступ.
5. `03-clone-api-repository.sh`
6. `04-create-api-postgresql.sh`
7. `05-configure-laravel-api.sh`
8. `06-verify-laravel-api.sh`

Все скрипты рассчитаны на запуск от `root`, кроме отдельной ручной проверки GitHub-доступа от пользователя `n1`.

Типовой запуск:

```bash
chmod 700 ./ИМЯ_СКРИПТА.sh
./ИМЯ_СКРИПТА.sh
```

`chmod 700` разрешает чтение, изменение и запуск файла только пользователю-владельцу.

## 00-audit-api-host.sh

### Назначение

Проводит первичный read-only аудит сервера перед установкой API.

Скрипт ничего не устанавливает и не изменяет.

### Что проверяет

- текущие дату и пользователя;
- версию ядра и дистрибутив;
- архитектуру и количество CPU;
- объём оперативной памяти и swap;
- файловые системы, диски и точки монтирования;
- процессы, использующие больше всего памяти;
- открытые TCP/UDP-порты;
- активные systemd-сервисы;
- наличие команд:
  - `nginx`;
  - `php`;
  - `composer`;
  - `git`;
  - `psql`;
- версии найденных компонентов;
- состояние сервисов:
  - `nginx`;
  - `php8.4-fpm`;
  - `postgresql`.

### Когда запускать

- перед первой установкой;
- при переносе на новую ноду;
- перед диагностикой нехватки памяти, конфликтов портов или отсутствующих пакетов.

### Повторный запуск

Безопасен. Скрипт только читает состояние системы.

## 01-install-api-runtime.sh

### Назначение

Устанавливает базовое серверное окружение для Laravel API.

### Что устанавливает

- Nginx;
- PHP 8.4 CLI;
- PHP 8.4 FPM;
- PHP OPcache;
- расширения PHP:
  - PostgreSQL/PDO PostgreSQL;
  - mbstring;
  - XML;
  - cURL;
  - ZIP;
  - BCMath;
  - Intl;
- Composer;
- PostgreSQL server и client;
- Git;
- `unzip`;
- корневые CA-сертификаты.

### Что делает перед установкой

- проверяет запуск от `root`;
- проверяет наличие `apt-get` и `apt-cache`;
- выполняет `apt-get update`;
- проверяет доступность каждого пакета в подключённых репозиториях;
- прекращает работу, если хотя бы один пакет недоступен.

### Что проверяет после установки

- версии Nginx, PHP, Composer, PostgreSQL и Git;
- наличие необходимых PHP-расширений;
- состояние Nginx, PHP-FPM и PostgreSQL;
- открытые порты.

### Что скрипт не делает

- не создаёт Nginx virtual host;
- не настраивает PHP-FPM pool;
- не создаёт базу данных;
- не настраивает firewall;
- не устанавливает TLS-сертификат.

### Повторный запуск

Обычно безопасен: `apt-get install` оставляет уже установленные пакеты без переустановки. При этом скрипт снова обновит индекс пакетов и проверит сервисы.

### Ограничение

Скрипт жёстко рассчитан на пакеты PHP 8.4. На системе, где репозиторий не предоставляет `php8.4-*`, он завершится до установки.

## 02-create-n1-user-and-ssh.sh

### Назначение

Создаёт системного пользователя `n1`, рабочий каталог проекта и SSH-ключ для доступа к GitHub.

### Что создаёт

- пользователя `n1`, если он ещё не существует;
- домашний каталог `/home/n1`;
- группу `n1`;
- shell `/bin/bash`;
- каталог `/srv/n1`;
- каталог `/home/n1/.ssh`;
- SSH-ключ Ed25519:
  - приватный ключ: `/home/n1/.ssh/id_ed25519`;
  - публичный ключ: `/home/n1/.ssh/id_ed25519.pub`.

### Права

- `/home/n1/.ssh` — `0700`;
- приватный ключ — `0600`;
- публичный ключ — `0644`;
- владелец SSH-файлов — `n1:n1`.

### Что выводит

- данные пользователя `n1`;
- права каталогов;
- публичный SSH-ключ, который нужно добавить в GitHub.

### Действия после запуска

Добавить выведенный ключ в GitHub и проверить подключение:

```bash
su - n1
ssh -T git@github.com
```

### Повторный запуск

Безопасен:

- существующий пользователь не пересоздаётся;
- существующий приватный ключ не заменяется;
- права на SSH-каталог и ключи приводятся к ожидаемому состоянию.

### Важное ограничение

Скрипт не добавляет ключ в GitHub автоматически. Это делается вручную через настройки GitHub.

## 03-clone-api-repository.sh

### Назначение

Клонирует production-репозиторий Laravel API в `/srv/n1/api`.

### Значения по умолчанию

- репозиторий: `git@github.com:Oleg4cy/n1-api.git`;
- ветка: `main`;
- каталог: `/srv/n1/api`.

### Что делает

- проверяет запуск от `root`;
- проверяет существование пользователя `n1`;
- выполняет клонирование от имени `n1`;
- клонирует только выбранную ветку;
- не использует shallow clone, поэтому история ветки сохраняется;
- задаёт локальные Git-настройки:
  - `pull.ff=only`;
  - `fetch.prune=true`;
- выводит:
  - URL `origin`;
  - текущую ветку;
  - upstream;
  - текущий commit SHA;
  - Git status.

### Поведение при существующем каталоге

Если `/srv/n1/api` уже является Git-репозиторием:

- проверяется URL `origin`;
- при совпадении скрипт не выполняет ни `clone`, ни `pull`;
- при несовпадении URL скрипт завершится с ошибкой.

Если каталог существует, но не является репозиторием:

- пустой каталог будет удалён перед клонированием;
- непустой каталог не будет затронут, скрипт завершится с ошибкой.

### Настраиваемые переменные окружения

```bash
N1_API_REPOSITORY_URL
N1_API_BRANCH
N1_API_DIRECTORY
```

Пример:

```bash
N1_API_BRANCH=develop ./03-clone-api-repository.sh
```

### Повторный запуск

Безопасен для уже клонированного корректного репозитория. Обновление кода повторный запуск не выполняет — для этого используется отдельный `git pull`.

## 04-create-api-postgresql.sh

### Назначение

Создаёт или проверяет PostgreSQL-роль и базу данных Laravel API.

### Значения по умолчанию

- роль: `n1_api`;
- база: `n1_api`;
- файл пароля: `/root/.n1-secrets/api-db-password`;
- подключение приложения: `127.0.0.1:5432`.

### Что создаёт

- защищённый каталог `/root/.n1-secrets`;
- случайный пароль PostgreSQL длиной 64 шестнадцатеричных символа;
- PostgreSQL-роль `n1_api`;
- базу `n1_api`;
- владельца базы `n1_api`.

### Права роли

Роль получает:

- `LOGIN`;
- подключение к своей базе;
- возможность создавать временные объекты.

Роль не получает:

- `SUPERUSER`;
- `CREATEDB`;
- `CREATEROLE`;
- `REPLICATION`;
- `BYPASSRLS`.

### Дополнительная настройка базы

- timezone базы устанавливается в `UTC`;
- общие права `PUBLIC` на базу отзываются;
- роли приложения явно выдаются `CONNECT` и `TEMPORARY`.

### Проверки

- наличие необходимых системных команд;
- формат сохранённого пароля;
- использование PostgreSQL `scram-sha-256`;
- подключение к базе от имени системного пользователя `n1`;
- текущий пользователь, база и timezone;
- свойства роли;
- владелец базы;
- права файла с паролем.

### Временный файл

Для теста создаётся:

```text
/home/n1/.pgpass.n1-api-test
```

Он удаляется при завершении скрипта, включая аварийное завершение через `trap`.

### Настраиваемые переменные окружения

```bash
N1_API_DB_USERNAME
N1_API_DB_DATABASE
N1_API_SECRETS_DIRECTORY
```

### Повторный запуск

Скрипт рассчитан на повторное использование:

- существующий пароль повторно используется;
- существующая роль не пересоздаётся;
- существующая база не пересоздаётся;
- владелец базы, timezone и права снова приводятся к ожидаемому состоянию.

### Важное замечание

Файл `/root/.n1-secrets/api-db-password` нельзя удалять без отдельного плана ротации пароля. Laravel использует этот пароль в `.env`.

## 05-configure-laravel-api.sh

### Назначение

Главный интерактивный скрипт настройки Laravel API.

Текущий файл `/root/init-laravel.sh`, который использовался при развёртывании, соответствует именно этому скрипту.

### Что проверяет перед началом

- запуск от `root`;
- наличие системного пользователя `n1`;
- наличие:
  - `artisan`;
  - `composer.json`;
  - `composer.lock`;
  - `.gitignore`;
- наличие необходимых системных команд.

### Работа с существующим `.env`

Если `/srv/n1/api/.env` существует, скрипт:

- считывает текущие значения как значения по умолчанию;
- сохраняет существующий `APP_KEY`;
- предлагает оставить существующие секреты нажатием Enter;
- перед заменой создаёт резервную копию в:

```text
/root/.n1-backups/laravel-env/
```

### Какие группы переменных запрашиваются

#### Приложение и домены

- `APP_NAME`;
- `APP_URL`;
- `FRONTEND_ORIGINS`;
- `SANCTUM_STATEFUL_DOMAINS`.

`APP_ENV` всегда записывается как `production`, а `APP_DEBUG` — как `false`.

#### Remnawave

- `REMNAWAVE_BASE_URL`;
- `REMNAWAVE_API_TOKEN`;
- `REMNAWAVE_ACTIVE_INTERNAL_SQUAD_UUIDS`;
- `REMNAWAVE_ACTIVE_EXTERNAL_SQUAD_UUID`;
- `REMNAWAVE_CONNECT_TIMEOUT`;
- `REMNAWAVE_REQUEST_TIMEOUT`.

Токен вводится скрыто.

#### Локализация, логирование и хеширование

- `APP_LOCALE`;
- `APP_FALLBACK_LOCALE`;
- `APP_FAKER_LOCALE`;
- `APP_MAINTENANCE_DRIVER`;
- `APP_MAINTENANCE_STORE`;
- `BCRYPT_ROUNDS`;
- `LOG_CHANNEL`;
- `LOG_STACK`;
- `LOG_DEPRECATIONS_CHANNEL`;
- `LOG_LEVEL`.

#### Платежи

- `PAYMENT_PROVIDER_DRIVER`;
- `PAYMENT_RETURN_URL`;
- `PAYMENT_STUB_CONFIRMATION_URL_BASE`;
- `PAYMENT_STUB_ALLOW_INSECURE_LOOPBACK`.

#### Коды входа

- `LOGIN_CODE_DELIVERY`;
- `LOGIN_CODE_LIFETIME_MINUTES`;
- `LOGIN_CODE_MAXIMUM_ATTEMPTS`.

Для production значение `LOGIN_CODE_DELIVERY=browser` отклоняется. Используется `mail`.

#### PostgreSQL

- `DB_HOST`;
- `DB_PORT`;
- `DB_DATABASE`;
- `DB_USERNAME`;
- `DB_PASSWORD`;
- `DB_TIMEZONE`.

При наличии `/root/.n1-secrets/api-db-password` этот пароль предлагается как существующий и не выводится на экран.

#### Сессии, очередь, кеш и файловая система

- `SESSION_DRIVER`;
- `SESSION_SECURE_COOKIE`;
- `SESSION_SAME_SITE`;
- `SESSION_COOKIE`;
- `SESSION_LIFETIME`;
- `SESSION_ENCRYPT`;
- `SESSION_PATH`;
- `SESSION_DOMAIN`;
- `BROADCAST_CONNECTION`;
- `FILESYSTEM_DISK`;
- `QUEUE_CONNECTION`;
- `CACHE_STORE`;
- `CACHE_PREFIX`;
- `MEMCACHED_HOST`.

#### Redis-совместимые параметры

- `REDIS_CLIENT`;
- `REDIS_HOST`;
- `REDIS_PASSWORD`;
- `REDIS_PORT`.

Redis может не использоваться текущей конфигурацией, но переменные сохраняются для совместимости с Laravel-конфигурацией.

#### Почта

- `MAIL_MAILER`;
- `MAIL_SCHEME`;
- `MAIL_HOST`;
- `MAIL_PORT`;
- `MAIL_USERNAME`;
- `MAIL_PASSWORD`;
- `MAIL_FROM_ADDRESS`;
- `MAIL_FROM_NAME`.

Пароль вводится скрыто.

При `MAIL_MAILER=log` письма не отправляются пользователю, а записываются в Laravel log.

#### AWS/S3-совместимые параметры

- `AWS_ACCESS_KEY_ID`;
- `AWS_SECRET_ACCESS_KEY`;
- `AWS_DEFAULT_REGION`;
- `AWS_BUCKET`;
- `AWS_USE_PATH_STYLE_ENDPOINT`.

#### Vite-совместимое значение

- `VITE_APP_NAME`.

Это значение сохраняется в Laravel `.env`, но frontend имеет собственный `.env` и настраивается отдельно.

### Проверка введённых данных

Скрипт проверяет:

- абсолютный формат HTTP/HTTPS URL;
- положительные числовые значения;
- значения `true`/`false`;
- формат UUID;
- список внутренних UUID через запятую;
- отсутствие переносов строк в секретах;
- допустимость режима доставки кода входа.

### Экран REVIEW

Перед записью выводится сводка без токенов и паролей.

Для продолжения нужно явно ввести:

```text
y
```

Enter на запросе `[y/N]` означает `N`, поэтому скрипт завершится без записи нового `.env`.

### Что выполняется после подтверждения

1. Создание резервной копии старого `.env`.
2. Запись нового production `.env`.
3. Настройка прав:
   - `.env` — `0600`, владелец `n1:n1`;
   - Laravel storage/cache — доступ для `n1`.
4. `php artisan optimize:clear`.
5. `composer install`:
   - без dev-зависимостей;
   - по `composer.lock`;
   - с оптимизированным autoload.
6. Генерация `APP_KEY`, только если корректного ключа ещё нет.
7. `php artisan migrate --force`.
8. Запуск `TariffCatalogSeeder`, только если файл существует.
9. Кеширование:
   - конфигурации;
   - событий;
   - Blade views.
10. Проверка Composer platform requirements.
11. Проверка `APP_ENV`.
12. Вывод статуса миграций.
13. Вывод таблиц базы.
14. Проверка health-маршрута.
15. Проверка того, используются ли Squad-переменные текущим кодом.
16. Запуск `remnawave:check`, если команда присутствует.
17. Проверка `APP_KEY`, прав `.env` и Git status.

### Повторный запуск

Допускается:

- существующий `APP_KEY` сохраняется;
- старый `.env` резервируется;
- `composer install` повторно не переустанавливает уже установленные пакеты;
- выполненные миграции не повторяются;
- кеши пересоздаются.

### Текущее ограничение production-ветки

В текущем `main` отсутствует:

```text
database/seeders/TariffCatalogSeeder.php
```

Поэтому скрипт завершает базовую настройку, но пропускает наполнение тарифов и выводит предупреждение.

Также обе Squad-переменные записываются в `.env`, но текущий checkout может их не использовать. Скрипт проверяет это и сообщает отдельно.

### Безопасность

- токены и пароли не выводятся;
- `APP_KEY` не показывается;
- старый `.env` сохраняется в защищённом каталоге;
- пароль PostgreSQL не удаляется;
- Git-репозиторий не изменяется.

## 06-verify-laravel-api.sh

### Назначение

Выполняет повторную безопасную проверку уже настроенного Laravel API.

Скрипт предназначен для контроля после настройки или обновления кода.

### Что проверяет

- наличие:
  - `artisan`;
  - `composer.json`;
  - `composer.lock`;
  - `.env`;
- владельцев и права:
  - `.env`;
  - `storage`;
  - `bootstrap/cache`;
- основные несекретные значения `.env`;
- наличие секретных значений без вывода их содержимого;
- соответствие платформы требованиям Composer;
- текущее Laravel environment;
- статус миграций;
- наличие health-маршрута;
- Git branch и наличие локальных изменений.

### Какие значения `.env` выводятся полностью

Только несекретные параметры, например:

- `APP_ENV`;
- `APP_DEBUG`;
- `APP_URL`;
- `FRONTEND_ORIGINS`;
- параметры базы без пароля;
- параметры session, queue, cache и mail driver.

### Как выводятся секреты

Для следующих переменных выводится только `configured` или `empty-or-missing`:

- `APP_KEY`;
- `DB_PASSWORD`;
- `REMNAWAVE_API_TOKEN`;
- `MAIL_PASSWORD`;
- `AWS_SECRET_ACCESS_KEY`.

### Повторный запуск

Безопасен. Скрипт не меняет `.env`, базу, миграции или Git-репозиторий.

## Что пока не входит в комплект

Эти скрипты покрывают только базовую подготовку Laravel API.

Пока отсутствуют отдельные скрипты для:

- Nginx virtual host;
- маршрутизации React и Laravel через один домен;
- настройки PHP-FPM;
- TLS/Certbot;
- systemd queue worker;
- systemd scheduler;
- автоматического deployment после `git pull`;
- резервного копирования PostgreSQL;
- logrotate;
- firewall;
- мониторинга;
- SMTP-сервера или внешнего SMTP;
- реального платёжного провайдера;
- наполнения тарифов, пока соответствующий seeder отсутствует в production-ветке.

Эти части должны добавляться отдельными скриптами после завершения соответствующих этапов развёртывания.
